# 三鼎多 Host 架构复盘：为什么失败，下次怎么不重犯

> 作者：CTO ｜ 日期：2026-11-14 ｜ 范围：dsh-web-control（控制面）+ 三台角色 Host + 驿传 v2 派单

---

## 1. 摘要

**一句话**：我们为"不存在的并发"付了钱，并且用最贵的手段（多进程 + fork 官方 UI）去实现一个最便宜的隔离层级（Session）。

三个数字：

| 项 | 值 |
| --- | --- |
| 投入 | 约 2 周 + 近 ¥1000 LLM 费用 |
| 保留的功能 | 0 个（控制面冻结，UI 回归官方） |
| 真实并发度 | ≈1（按开发流程串行推进） |

**结论**：单 Host 不是妥协，是回到正确的隔离层级。省下来的复杂度应该投到流程、验收、交付质量，而不是"把三个 UI 拼成一个"。

---

## 2. 事实账

| 维度 | 计划 | 实际 |
| --- | --- | --- |
| 拓扑 | 3 台角色 Host + 1 个统一控制面 | 同上，但控制面需 fork 官方 UI |
| 隔离目标 | 每个阶段上下文独立 | 三台共享同一个 `/workspace`，文件层没有隔离 |
| 派单 | 按任务类型路由到对应 Host | `worker_kinds` 是唯一派单输入，且单 worker 单租约 |
| 使用模式假设 | 三个角色并行工作 | 需求→设计→拆解→开发，串行 |
| 最终状态 | — | 控制面废弃，改 Caddy 子域反代官方 UI |

---

## 3. 决策链复盘（错在哪一步）

| # | 当时的决策 | 当时的理由 | 实际后果 |
| --- | --- | --- | --- |
| 1 | 需求被表述为"要一个多 Agent 统一控制面" | 三个角色要在一个界面里管 | 直接进入实现，没有人先问"为什么需要三个进程" |
| 2 | 选择 fork 官方 UI | 最短路径满足"一个界面" | 分叉在最复杂、最易变的层；上游每次改 UI/协议都要跟 |
| 3 | 三台 Host 的拓扑被"一个 profile 只装一个角色包"反向决定 | 角色包都占 `registry.default` 与人设槽位 | 实现细节绑架了拓扑；后来证明这两个冲突都能修 |
| 4 | 用"一台 Host 只声明一组 kind"表达角色路由 | 能跑，配置简单 | 隐式契约；一合并就必须显式化，且规则与代码一度相反 |
| 5 | 控制面直接依赖 dsh 的联邦转发与事件流 | 那是当时唯一能拿到数据的路 | 依赖的是内部契约：projection 不转发、Node WS 带不上 cookie，修一个漏一个 |
| 6 | 用单测绿 + 手工点页面作为验收 | 快 | 单测验证实现，不验证"用起来对不对"；真实并发假设直到用了几周才暴露 |

---

## 4. 五条根因（按代价排序）

### 4.1 用架构推演代替使用观察

- 当时：假设三个角色并行，按并行设计拓扑。
- 实际：串行流程，并发≈1。这个事实几天真实使用就暴露了，但我们先花两周把它造出来。
- 代价：整个多 Host 与多 Worker 的复杂度，收益为 0。

### 4.2 把"隔离"错误地映射到"主机"

- 真正要的：每个阶段的上下文关注点不同 → 这是 **Session** 级隔离。
- 实际选的：三台 Host → 买到的是进程/部署隔离，附带三份 home、三份升级、三个入口、跨 Host 通信。
- 更糟的是：三台共享同一个工作区，文件层根本没隔离——**付了进程隔离的成本，没拿到进程隔离的收益**。

### 4.3 fork 官方 UI，用上游红利换维护负债

- 分叉点选在最复杂、最易变的层（UI + 会话协议），而不是稳定的扩展点（插件、preset、patch）。
- 结果：上游每次演进都是我们的负债，而我们没有维护上游的能力与预算。

### 4.4 在别人的内部契约上盖房子

- 联邦会话的 projection 帧、`api-session/status` 事件通道，都不是公开 API。
- 表现：修好列表刷新，圆点还坏；修好圆点，事件通道本身又带不上 cookie。
- 规律：**依赖内部契约的功能，修复成本不是线性的，是"每层都可能漏"的。**

### 4.5 隐式契约用部署拓扑表达

- 角色 → 任务的映射藏在"哪台 Host 声明了哪些 kind"里。
- 一旦要合并，这个映射必须显式化——而它此前从未被写下来，导致设计文档与代码一度相反（"kind 不做路由" vs "kind 是唯一派单输入"）。
- 规律：**能跑的隐式约定，是最贵的债。**

## 5. 哪些是错，哪些是当时合理

复盘要避免结果偏见，区分清楚：

| 决策 | 判定 | 说明 |
| --- | --- | --- |
| 尝试统一控制面 | 合理 | 需求真实存在，问题在实现路径 |
| 角色拆成独立包 | 合理 | 角色资产、技能、人设确实不同 |
| 驿传按 kind 派单 | 合理 | 任务类型是真实维度，问题在"用 Host 表达角色" |
| 假设并行 | 错误 | 未观测就写进架构 |
| fork UI | 错误 | 违反"不与上游对抗"原则 |
| 依赖内部契约 | 错误 | 未评估契约稳定性与回归成本 |
| 无 kill criteria | 错误 | 两周内没有任何"停止"的触发条件 |

---

## 6. 遗留资产（不是零产出）

1. **dsh 内部边界知识**：联邦转发、projection 分层、事件通道的限制——这些让单 Host 方案变得简单，不是白学。
2. **`dsh-portal`**：Caddy 子域反代 + 门户页，正好接住这次回归。
3. **驿传 v2**：派单、租约、心跳本身没问题，问题在"按 Host 分工"的用法。
4. **三个角色包 + 技能体系**：继续用，只是资产从宿主层下沉到 preset 层。
5. **一条用钱买来的结论**：知道"不要做什么"。

---

## 7. 六条可复用原则

1. **先测工作流，再定拓扑**：一周真实使用日志 > 任何架构推演。
2. **隔离先问"隔离什么"**：上下文 → Session；权限/故障域 → 容器；升级节奏 → 仓库。四者不能混。
3. **不 fork 上游 UI/协议**，只在稳定扩展点（插件、preset、patch）上做。
4. **依赖内部契约前先确认它是不是公开契约**；不是的话，预算里必须写"每次升级回归"。
5. **每个架构决策配 kill criteria + 时间盒**；到期不达标就回退，不续命。
6. **隐式契约显式化**：角色/能力映射写进配置，不靠部署拓扑。

## 8. 架构选型检查清单（下次评审直接用）

任何跨进程/跨仓库/改上游的方案，逐条回答，**有一条答不上就先停**。

**前提类**

1. 这个需求背后的真实工作流是什么？有没有一周的真实日志或使用数据支撑？
2. 不做的代价是什么？如果两周后不做，业务会损失什么？
3. 我们要隔离的到底是什么——上下文、权限、故障域，还是升级节奏？分别对应哪一层？

**成本类**

4. 这个隔离能否用更低的层级实现？两层方案的维护成本差多少（部署、升级、排障）？
5. 是否要修改/fork 上游？分叉点在哪一层？上游的演进频率如何？谁来跟？
6. 依赖的是公开契约还是内部实现？如果是内部实现，回归成本是否写进了预算？

**执行类**

7. 验证回路多长？能否压到 30 秒（本地）或 5 分钟（容器）？
8. 隐式约定有哪些？能否全部写成显式配置或文档？
9. kill criteria 是什么？时间盒多长？到期由谁判定？
10. 回滚需要多久？回滚后数据与状态怎么处理？

**红线（出现即重新设计）**

- "先统一入口，再想怎么路由"
- "用部署拓扑表达业务语义"
- "在别人的内部 API 上盖房子"
- "单测绿 = 可用"
- "并行/高并发"没有观测数据支撑
- 为了短期体验分叉上游

## 9. 时间盒与 kill criteria 模板

```
方案：<名称>
假设：<必须在现实中被验证的假设，如"三角色并行" >
观测指标：<可测量，如"一周内并发任务 ≥2 的天数占比">
达标线：<如 ≥20%>
时间盒：<如 2 周>
判定人：<如 用户>
回退方案：<如 单 Host + 多 preset>
回退成本：<如 半天>
```

本次反推：如果一开始写了这条，"并发 ≥2 的天数占比 <20% → 回退"，第一周就会触发回退，能省下约 1.5 周和大部分费用。

---

## 10. 这次重构（V3）如何体现这些规则

| 原则 | 在 V3 中的落点 |
| --- | --- |
| 先测工作流 | 已用真实使用确认串行，单 Host |
| 隔离分层 | 隔离单位下移到 Session（`项目:角色`） |
| 不 fork 上游 | 回归官方 UI，Caddy 只做反代 |
| 只用稳定扩展点 | 角色资产走 preset 插件，不改 dsh 内核 |
| 显式契约 | `kind → preset` 写进平台配置 |
| 显式化语义 | 注册表 default 只由一个包写，其余包不重复插入 |
| 短反馈 | 先在本地 profile 验证技能可见性，再动部署 |
| 可回滚 | 旧三台保留到收口阶段 |
